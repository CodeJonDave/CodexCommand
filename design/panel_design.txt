# Asset 04 — Panel Visual System

## Status

Design is not complete until explicitly confirmed complete.

Creation, implementation, and testing remain paused until this document is accepted as the authoritative Asset 04 design framework.

---

## 1. Purpose

Asset 04 defines the visual, structural, behavioral, and asset architecture for the Codex Command panel system.

Asset 04 covers only:

* Mission Status Bar
* Operations Panel
* Workspace navigation as hosted by the Operations Panel
* Structural status rails
* Embedded status markers
* Panel drawers
* Panel asset architecture

Asset 04 does not define:

* Widget Visual System
* Typography System
* Iconography System
* Window Decoration
* Application Style
* Notifications
* Lock Screen
* Login / SDDM
* Sounds
* Animations
* Dashboard / Telemetry Visualization

Asset 04 establishes the command-surface structure that later assets will occupy.

Status Zone elements may expose inspection and quick common actions.

Status Zone elements may not become primary control surfaces.

Complex actions, administration, navigation, and system management remain Operations Panel responsibilities.

---

## 2. Design Doctrine

Codex Command panels follow the FCV CC-01 command-interface doctrine:

* Status > Decoration
* Function > Atmosphere
* Readability > Effects
* Operational Awareness > Visual Spectacle
* Information Density > Empty Space
* Responsiveness > Visual Fidelity

The panels must visually read as:

* Fleet command console surfaces
* Integrated command surfaces
* Operational control rails
* Shipboard mission interface panels

The panels must not visually read as:

* Standard desktop panels
* Consumer desktop chrome
* Application docks
* Gaming HUDs
* Neon sci-fi decoration
* Glass panels

Forbidden visual elements:

* Glassmorphism
* Heavy blur
* Rounded consumer styling
* RGB effects
* Neon borders
* Excessive transparency
* Decorative ornamentation
* Pseudo-3D effects
* Glow effects
* Gradients used as decoration

## 7. Shared Panel State Architecture

Both panel systems use the same panel-state model:

* READY
* OPERATIONAL
* ATTENTION
* DEGRADED
* CRITICAL

Each panel owns its own state independently.

Valid example:

* Mission Status Bar: OPERATIONAL
* Operations Panel: DEGRADED

State-source authority:

* Highest severity source determines panel state.

State transition model:

* Hybrid

Escalation:

* Automatic

Recovery:

* Operator confirmed

Escalation path:

READY
→ OPERATIONAL
→ ATTENTION
→ DEGRADED
→ CRITICAL

Recovery path:

CRITICAL
→ DEGRADED
→ ATTENTION
→ OPERATIONAL
→ READY

Recovery rules:

* Recovery may not skip states.
* Recovery is not automatic.
* Recovery requires operator confirmation.
* Each recovery step must be confirmed independently.

Operational classification to panel-state mapping occurs through a translation layer.

State relationship rules:

* Panel-state transitions do not generate markers.
* Markers exist to notify.
* Panel state exists to represent current condition.
* Acknowledging a marker does not affect panel state.
* Only underlying conditions may alter panel state.

Failure behavior:

* If a panel cannot determine its state, it enters fail-safe behavior.

Startup behavior:

* Panels initialize as STATE UNKNOWN until authoritative state sources are evaluated.

Session restore behavior:

* Panel state is re-evaluated.
* Saved session state is not trusted as current condition.

Multi-monitor failure behavior:

* Operations Panel failure is local to the affected monitor.
* Other Operations Panels continue operating.
* Mission Status Bar continues operating unless its own state authority fails.

Accessibility rule:

* State and severity communication use color only, supported by position, ordering, and persistence.
* Shape, geometry, and size variants are not required for accessibility within Asset 04.

Performance priority:

* Responsiveness
* Readability
* Visual fidelity

Classification:

* Panel structure
* Not decoration
* Not widget
* Not ordinary indicator

Placement rule:

* Rail sits on the panel edge furthest from the screen edge.

Mission Status Bar rail:

* Bottom edge

Operations Panel rail:

* Left edge

Rail visibility:

* Rail remains visible when panel is hidden.

Rail width:

* 3–4 px

Rail type:

* Solid rail with embedded status markers

Rail purpose:

* Persistent operational awareness
* Panel state visibility
* State recognition while panel is hidden

Rail base color authority:

* Panel state

Rail base color mapping:

* READY → Bright Green
* OPERATIONAL → Forest Green
* ATTENTION → Bright Yellow
* DEGRADED → Reddish Orange
* CRITICAL → Bright Red

Rail appearance with no markers:

* Solid state rail

Rail appearance with overflow markers:

* Inline

Rail ownership:

* Mission Status Bar rail represents Mission Status Bar state.
* Operations Panel rail represents Operations Panel state.

## 12. Embedded Status Marker System

Embedded markers are part of the structural rail.

Marker type:

* Embedded line segment

Marker appearance:

* Flat
* Single-color segment
* No bevel
* No emboss
* No glow
* No gradient
* No pseudo-3D treatment

Marker geometry:

* Uniform
* Same size regardless of severity

Marker length:

* 4–8 px

Marker spacing:

* 2 px

Maximum visible marker capacity:

* 32 markers

Marker severity communication uses:

* Color
* Ordering
* Position
* Persistence

Marker severity does not use:

* Size scaling
* Area scaling
* Visual dominance scaling

Marker persistence:

* Latched

Marker acknowledgement:

* Per marker

Acknowledgement scope:

* Individual marker

Marker ordering:

* Hybrid
* Severity first
* Chronological within severity

Marker placement:

* Ordered rebuild

Marker capacity:

* Fixed

Overflow behavior:

* Per-severity merge

Overflow representation:

* Compressed segment + count

Overflow placement:

* Inline with normal marker stream

Marker color authority:

* Operational Classification System

Rail interaction:

* Interactive

Interaction philosophy:

* Inspect first

Clicking or selecting a marker:

* Opens inspection
* Does not automatically acknowledge

Acknowledgement:

* Separate intentional operator action

Inspection location:

* Panel drawer

Marker lifecycle:

1. Event occurs.
2. Marker is created.
3. Marker latches.
4. Marker remains even if condition clears.
5. Operator selects marker.
6. Panel drawer opens.
7. Operator inspects details.
8. Operator acknowledges marker or leaves it latched.
9. If acknowledged, individual marker is removed.
10. Rail is rebuilt according to ordering rules.

* Technical dividers

Footer structure:
